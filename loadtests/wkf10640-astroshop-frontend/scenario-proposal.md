## Risks & unknowns
- **R1 (sampling blindness).** Source sampling ratio = 1.0 (`Sampled: no` on this tenant → unsampled). Rare / error / retry-storm journeys are still under-represented at extraction; weights reflect the observed window only. Error-rate baselines read 0.0 because no error spans fell in the window — not a guarantee of an error-free path.
- **R2 (mean ≠ peak).** This model captures *mean* arrival over the window. No peak-envelope / 'peak vs typical' profile exists yet (separate backlog). CoV is low here so mean ≈ peak is tenant luck, not a modeled guarantee.
- **R5 (instrumentation coverage / circular ground truth).** Extraction and later validation draw from the same telemetry; shared blind spots — async fan-out, Kafka consumers, websockets, fire-and-forget — are invisible on both sides. At least one run should be cross-checked against infra metrics (CPU/connections), not telemetry alone.
- **R5 session signal (Path B — OTel `session.id` on spans).** `session.id` coverage **20.12%** across the reported session-bearing services; present on: `ad` 20.38% (5241 sessions), `smartfreight-agent-service` 5.47% (131 sessions). Where present, journeys are stitched from real session chains (ordered actions + measured think-times) rather than span-order inference; elsewhere the span-order method (tiers 2a/2b) is the unchanged fallback. No RUM / classic-token dependency (Path A is board-gated; ISI-5691 NO-GO on Grail-only RUM).
- **Access logs unavailable -> spans-only extraction.** The istio-proxy access-log probe returned 0 lines; the HTTP surface was recovered from frontend server-span `span.name` routes. x-request-id chaining is therefore unavailable; journey steps are reconstructed from the trace span-tree.
- **Window hygiene caveat.** wkf10640 is a shared, continuously-deployed demo playground: the target service (SERVICE-39720C1E0047A5C0, astroshop frontend) saw 3 CUSTOM_DEPLOYMENT events and the tenant 31 Davis problems in the 3h window. Same-image demo redeploys; baselines are computed over 810,116 server spans so transient deploys do not dominate. A stricter run should shrink to a deploy-free sub-window.
- **Weights are per-outcome.** Buyer ~0.9%, Browser ~99.1% of entry traffic (2,810 vs 303,223 of 306,033 frontend root traces that do / do not reach checkout/payment).
- **R1 sampling.** dt.system.sampling_ratio = 1.0 on frontend root spans (no sampling correction applied).
- **R5 session-chaining (Path B applied, partial).** An OTel `session.id` IS present on the `ad` service (20.4% of its spans; 5,241 browse sessions, mean 5.3 ad-slot loads each) but NOT on the frontend/checkout/payment spans. So the **Browser** journey's inter-page think-time is now the MEASURED session-chain distribution (p50 7.2s / p90 27.7s / p99 45.1s, session span p50 47s) instead of a span-order assumption. The **Buyer** (checkout) path carries no session.id and is still reconstructed from self-contained checkout traces (browse->cart->checkout). End-to-end session stitching would need session.id propagated as baggage across all frontend services (OTel session semconv); see ISI-5693 / ISI-5691 (Path A RUM fusion remains board-gated).
