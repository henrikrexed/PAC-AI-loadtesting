## Risks & unknowns
- **R1 (sampling blindness).** Source sampling ratio = 1.0 (`Sampled: no` on this tenant → unsampled). Rare / error / retry-storm journeys are still under-represented at extraction; weights reflect the observed window only. Error-rate baselines read 0.0 because no error spans fell in the window — not a guarantee of an error-free path.
- **R2 (mean ≠ peak).** This model captures *mean* arrival over the window. No peak-envelope / 'peak vs typical' profile exists yet (separate backlog). CoV is low here so mean ≈ peak is tenant luck, not a modeled guarantee.
- **R5 (instrumentation coverage / circular ground truth).** Extraction and later validation draw from the same telemetry; shared blind spots — async fan-out, Kafka consumers, websockets, fire-and-forget — are invisible on both sides. At least one run should be cross-checked against infra metrics (CPU/connections), not telemetry alone.
- **Journeys are behavioral archetypes, not endpoints.** Steps were reconstructed from the trace span-tree (`collectArray` over `sort start_time asc`). The Buyer funnel's downstream fan-out (PlaceOrder → GetCart → GetProduct×N → Convert×N → shipping quote → payment Charge → ship-order → EmptyCart → email) is captured as the checkout step's reach-12 signature; the driver replays the 4 user-facing HTTP steps and the backend funnel follows.
- **R5 / session-chaining limit.** The locust driver carries no persistent session id on browse spans (`app.user.id` appears only on cart/checkout), so browse→buy cannot be chained across independent tasks. The Buyer archetype is therefore reconstructed from the self-contained checkout_* traces (which internally browse→cart→checkout). A real production front-end with a `session.id` cookie would let SCOPE chain full sessions.
- **Weights are per-outcome.** Buyer ≈6.1%, Browser ≈93.9% of entry traffic (share of flows that place an order vs not), summed from the order-split query.
